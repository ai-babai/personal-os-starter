# Personal OS в BB

Читать при подключении OS к BB или работе с его потоками и окружениями.
Для обычной задачи в знаниях достаточно корневых инструкций Personal OS.

Источник: [Personal OS Starter — ветка system](https://github.com/ai-babai/personal-os-starter/blob/design/system-layout/clients/bb.md).
Команды сверены со справкой BB **0.48.1**. На другой версии сначала проверь
`bb guide` и `bb <команда> --help`; пример не заменяет действующий контракт CLI.

## Подключение к личной OS

1. Определи реальный хост и папку: `bb status --json`. Интерфейс BB может быть
   открыт на другом устройстве. Существующий проект OS используй повторно.
2. Для знаний выбери проект с уже существующим корнем, окружение **Project checkout**.
   Память и заметки должны попадать в каноническую папку. Отдельный worktree
   самой Personal OS для онбординга не нужен.
3. Сохрани этот файл в `system/tools/clients/bb.md` относительно личного корня и добавь
   ссылку в `system/tools/INDEX.md`. Исходник можно взять из комплекта или по
   [прямой ссылке](https://raw.githubusercontent.com/ai-babai/personal-os-starter/design/system-layout/clients/bb.md).
   Существующую локальную версию сначала сравни; пользовательские дополнения сохрани.
4. Для постоянного входа добавь короткий блок в `.bb/AGENTS.md` внутри корня OS.
   Сохрани прежние инструкции. Текст блока:

   ```text
   Personal OS находится в корне этой рабочей папки.
   Начни с README.md, AGENTS.md и system/agent/BOOTSTRAP.md.
   Перед работой с BB прочитай system/tools/clients/bb.md.
   Подробности знаний раскрывай только по текущей задаче.
   ```

5. Проверь в **новом чате**, что агент находит корень, профиль и точку продолжения.
   BB подхватывает `.bb/AGENTS.md` при старте сессии. Корневой `AGENTS.md` также
   может читать сам провайдер; не полагайся на одинаковое поведение всех провайдеров.

Глобальный `<dataDir>/AGENTS.md` действует на все проекты этого профиля BB.
Для первого подключения используй локальный вход выше. При необходимости общего
указателя сначала согласуй его область; фактический data dir показывает `bb status`.
Подробности: `bb guide agent-configuration`.

## Работа с клиентом

- Начинай с `bb status`; нужную часть справки выбирай через `bb guide`.
- Имена сессий задавай штатно: `bb thread update --self --title "[os]-Тема"`.
  После первичного именования сохраняй название до решения владельца.
- Перед действием с другим потоком, проектом или окружением уточни его ID.
  В командах запуска указывай проект и выбранное окружение явно.
- Многострочное задание передавай через `--prompt-file`, сообщение — через
  `--message-file`. Не вставляй Markdown с shell-подстановками в аргументы команды.
- Проверяй реальные файлы и результат команды. История чата сама по себе
  не заменяет актуальное состояние проекта.

## Подагенты — когда задача требует делегирования

Запускай дочерний поток только в рамках явно разрешённого делегирования.
Наличие этой инструкции не является таким разрешением. Короткую задачу проще
закончить в текущем чате; отдельному агенту нужна самостоятельная часть работы.

Перед запуском прочитай `bb guide threads` и `bb guide providers`. Посмотри
`bb provider list --environment ENVIRONMENT_ID`, а при явном выборе модели —
`bb provider models PROVIDER_ID --environment ENVIRONMENT_ID`.
Подставляй ID из фактической среды. Учитывай выбор владельца и доступный бюджет;
не переноси из примеров чужие модели, подписки и разрешения.

В файле задания укажи цель, нужный контекст, разрешённые файлы/действия,
ожидаемый результат и способ проверки. Для ревью явно задай режим **только чтение**.
Передай только контекст подзадачи, без всей личной базы и credentials.

Пример создания дочернего потока из текущего BB-чата. Значения `PROJECT_ID`,
`ENVIRONMENT_ID` и `TASK_FILE` нужно заменить перед выполнением:

```text
bb thread spawn --project PROJECT_ID --environment ENVIRONMENT_ID --parent-self --title "[os]-Проверка ссылок" --prompt-file TASK_FILE
```

По выбранным условиям добавь `--provider`, `--model` и `--reasoning-level`
с поддерживаемыми значениями. Не расширяй permission mode ради удобства запуска.

- `--parent-self` связывает поток с текущим родителем. По умолчанию уведомления
  `auto` возвращают завершение и блокеры родителю.
- `--environment` даёт ребёнку нужную рабочую папку. Без явного выбора BB может
  создать новое окружение; тогда ребёнок не увидит текущие незакоммиченные правки.
- В общей папке назначь одного автора каждого файла. Ревьюер читает;
  независимые изменения кода могут выполняться в отдельных проектных worktree.
  Не разветвляй личную память OS ради параллельности.
- При `parent-notifications: stuck` или `off` ребёнок должен отдельно отправить
  результат родителю через `bb thread tell`; проверь настройку в `bb status`.

После запуска сохрани возвращённый ID. Дождись события штатным способом,
не устраивай частые опросы статуса. Пока ожидаешь, выполняй независимую работу.
Например, ограниченное ожидание и чтение результата:

```text
bb thread wait CHILD_ID --timeout 45s
bb thread output CHILD_ID
```

Тайм-аут не означает завершение: при ошибке или блокере прочитай `bb thread show`
и `bb thread log`, затем реши конкретную проблему. Уточнение ребёнку отправляй
через `bb thread tell CHILD_ID --message-file MESSAGE_FILE`.
Родитель проверяет результат и включает его в общий итог. Не удаляй и не архивируй
чужие потоки или окружения как автоматическую «уборку».

## Возможности по мере необходимости

Штатные BB-навыки раскрывай по задаче: CLI, провайдеры, Git, публикация порта,
автоматизации. Используй уже установленные инструкции (`bb skill list`);
не копируй всю библиотеку в OS и не создавай skill для каждого документа.
Расписания, уведомления и внешние отправки остаются отдельными поручениями.

Источники: локальные `bb guide threads`, `bb guide providers`,
`bb guide agent-configuration` и [официальное руководство по координации агентов](https://getbb.app/guides/orchestrate-coding-agents).
