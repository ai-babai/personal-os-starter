# Работа с публичным шаблоном

Начни с [INDEX.md](INDEX.md). Это публичный комплект для разных людей.

- README объясняет пользу и принципы; в нём есть короткое поручение для передачи
  агенту. Единственный порядок развёртывания — [онбординг для агента](onboarding/README.md).
  Пиши его как действия, условия и проверяемый результат для агента.
  При установке начинай с него; читать весь комплект не нужно.
- Ядро не зависит от клиента и модели. Конкретные клиентские процедуры живут в `clients/`
  и открываются через [каталог](docs/CLIENTS.md) только при необходимости.
- Сохраняй progressive disclosure: короткий старт, затем только нужная область,
  задача и справочник. Не превращай подключение в чтение всего репозитория.
- `workspace/` — готовые нейтральные документы. Их содержимое переносят в выбранный
  владельцем корень. Имя папки, букву диска и операционную систему не фиксируй заранее.
  Локальную копию агент адаптирует по [онбордингу](onboarding/README.md#3-подготовь-личную-папку)
  после осмотра среды; исходник остаётся общим.
- Минимализм — принцип комплекта: достаточный текст и существующие возможности
  клиента. Любая новая обязательная программа требует реальной необходимости.
- При сопровождении шаблона добавляй подсказки под наблюдённые затруднения.
  После повторных экспериментов убирай подсказки, которые больше не помогают;
  не превращай их в постоянный обязательный процесс.
- Сохраняй простой вход: папка, агент, знакомство, первая задача.
  Базовый запуск должен работать обычным копированием документов. Автоматизация
  допустима как необязательное удобство по реальной задаче, без зависимости от неё.
- Не копируй приватную OS, её историю, аккаунты и токены в публичный комплект.
- При изменениях сохраняй один источник правила и рабочие относительные ссылки.
- Не перезаписывай существующие личные установки; обновляй выбранные документы
  с учётом их содержимого и разрешений владельца.
- Не добавляй постоянные тесты/CI без согласования владельца проекта.
  Ссылки и копирование можно проверить во временной папке вне репозитория.
- Перед публикацией проверь diff на личные сведения и секреты.

Правила личной OS находятся в [workspace/AGENTS.md](workspace/AGENTS.md).

# Онбординг для агента

Ты разворачиваешь Personal OS для владельца. Выполняй шаги сам доступными
инструментами; у человека уточняй только недостающие решения. Не отправляй
его читать этот документ или выполнять команды, которые можешь выполнить сам.

Пиши коротко, спокойно и дружелюбно, прямыми предложениями. Предлагай разумный
вариант. Не используй обороты вида «не X, а Y» и не злоупотребляй длинными
и короткими тире. В чате достаточно решений и существенных последствий;
технические подробности оставляй в материалах задачи.
Объясняй, что предлагаешь сделать и зачем. Ссылаться на требования инструкции
в обычном предложении плана не требуется.

**Результат:** личная папка в выбранном месте, фактическая среда в `AGENTS.md`,
минимальный подтверждённый профиль и первый полезный результат.

## 1. Определи исходное состояние

- Осмотри доступное в указанном владельцем месте, проверь фактические ОС хоста,
  оболочку и доступ к файлам. При удалённой работе ориентируйся на машину с файлами.
  Прочитай имеющиеся инструкции и карту; имена и пути могут отличаться от шаблона.
- Используй известные ответы. Если намерение или необходимые решения ещё неясны,
  до установки задай один-два уместных вопроса, предложи подходящий вариант. Если корень ещё
  не выбран, согласуй его до записи личных файлов. Допустим любой путь, в том числе
  `D:\` или `D:\PersonalOS`. Не спрашивай разрешение на уже конкретно порученное.
  Если для выбора нужно объяснение, кратко опиши: `personal/` хранит знания,
  профиль и предпочтения, `projects/` хранит личные и рабочие проекты,
  `system/` хранит память агента, инструменты и общие правила.
- Если в выбранном месте уже есть материалы или правила:
  - Для обычной задачи продолжи по старой карте с шага 5, без повторной установки.
  - Для перехода на этот стартер открой [миграцию в две фазы](MIGRATION.md).
    Это относится и к папке, которая раньше не называлась OS.
    Если комплект ещё не получен, сначала выполни шаг 2. До согласования плана
    сохраняй исходное состояние, включая инструкции и структуру разделов.
    Не начинай повторное знакомство.
  - Если намерение неясно, уточни: продолжить работу или перенести структуру.

Не сканируй весь диск: соседние папки не входят в OS автоматически.
Если нужного доступа нет, обозначь ограничение и одно конкретное действие
владельца, которое позволит продолжить. Не заявляй о выполненной установке.

## 2. Получи комплект, если его ещё нет

Если нужная версия репозитория уже клонирована или ZIP распакован, используй
эту копию. Иначе получи **main** в отдельный каталог для исходного шаблона.
Если в поручении задан commit или другая ветка, используй именно их:

| Условие | Действие |
|---|---|
| Git доступен | Выполни команду ниже из каталога для исходников |
| Git отсутствует | Скачай [ZIP ветки](https://github.com/ai-babai/personal-os-starter/archive/refs/heads/main.zip) и распакуй доступными средствами ОС |

```sh
git clone --branch main https://github.com/ai-babai/personal-os-starter.git
```

Для заданного commit после клонирования выполни `git checkout <commit>`
в каталоге исходников; вместо ZIP ветки используй
`https://github.com/ai-babai/personal-os-starter/archive/<commit>.zip`.
Ветку можно использовать для знакомства, сравнение агентов фиксирует commit.

Команда подходит для PowerShell и терминалов macOS/Linux. При занятом имени
каталога используй существующую копию этого шаблона или другое свободное имя;
не перезаписывай чужие файлы. Git, Python и Node.js устанавливать ради стартера
не нужно. ZIP содержит те же документы, что Git, без истории `.git`.

Примени [правила исходного репозитория](../AGENTS.md). Для установки достаточно
этого онбординга и входных файлов `workspace/`; продуктовый README и все
справочники подряд читать не требуется.

## 3. Подготовь личную папку

Этот шаг выполняй для новой OS. При наличии материалов или правил и переходе
на стартер следуй [инструкции миграции](MIGRATION.md).

Скопируй **всё содержимое `workspace/`** в выбранный корень, включая `.gitignore`
и `LICENSE`. Пользуйся средствами обнаруженной ОС; обязательного установщика нет.
Базовые разделы создаются сразу; конкретные проекты и подключения добавляются
по задаче. Постепенное чтение документов не означает выборочное копирование.

При установке и миграции используй готовые документы как основу: заполняй
фактическую среду и подтверждённые сведения, добавляй локальные уточнения.
Сохраняй общие правила и назначение разделов. Профессия владельца помогает
наполнить разделы; OS сохраняет общее назначение для личных и рабочих задач.
При объединении действующих правил с шаблоном сохрани смысл обоих источников,
убери дубли. Существенный конфликт или изменение правил представь владельцу
для решения. Дальнейшие изменения документов определяются задачами владельца.

Перед записью проверь совпадающие пути. Добавляй отсутствующее, а существующие
документы дополняй выборочно по смыслу. Сохраняй профиль, память, локальные
правила и настройки клиента. Пустой шаблон не заменяет заполненный документ.
Если конфликт нельзя разрешить без выбора владельца, уточни только его.

Исходный шаблон и личная OS — разные наборы файлов. Не заполняй профиль внутри
репозитория шаблона, не переноси его `.git` и не отправляй личные данные в его
публичный remote. Не меняй соседние папки и настройки существующего репозитория владельца.

## 4. Настрой вход и познакомься

Дальше работай в корне личной OS:

1. Прочитай `INDEX.md`, примени `AGENTS.md` и выполни `system/agent/BOOTSTRAP.md`.
   По карте открывай только область текущего шага.
2. Составь раздел «Локальная среда» в `AGENTS.md`: фактическая ОС хоста,
   абсолютный корень OS и используемая оболочка. Сохрани остальные правила;
   неизвестное отметь явно, версии не угадывай. При переносе перепроверь сведения.
3. Из запроса и существующего профиля возьми уже подтверждённые ответы.
   При необходимости задай один-два вопроса для текущего шага: как обращаться к
   владельцу, какой язык и стиль общения выбрать или с какой задачи начать.
   Остальное уточняй по мере работы. Не задерживай полезную
   работу ради необязательных ответов. Запиши подтверждённое в
   `personal/profile.md` и `personal/preferences.md` с датой и основанием.
   При заполнении заменяй противоречащие данным стартовые заглушки.
4. Если требуется постоянный вход или особенность клиента, открой нужную
   строку [каталога клиентов](../docs/CLIENTS.md). Возьми только соответствующую
   инструкцию из комплекта либо по ссылке той же версии и выполни её локальное
   подключение. Не устанавливай все клиентские пакеты заранее.

Имя и подробную роль агента, личную историю, проекты и инструменты раскрывай
по мере задач. Не переноси личность и настройки автора шаблона. Онбординг сам
по себе не разрешает запуск субагентов, отправку сообщений, подключение аккаунтов
или платные действия.

## 5. Выполни первую задачу и сохрани продолжение

Реши выбранную владельцем задачу в пределах её полномочий. Что сохранять,
определяет [правило передачи](../workspace/system/agent/protocols/handoff.md):
ожидаемые артефакты и изменения состояния задачи, без обязательного документа
на каждый разговор. Не создавай демонстрационный проект ради заполнения папок.

## Проверка результата

- Файлы находятся в выбранном корне; вход через `INDEX.md`, `AGENTS.md` и
  `system/agent/BOOTSTRAP.md` работает, нужные относительные ссылки разрешаются.
- Локальная среда соответствует проверенным фактам; профиль содержит только
  подтверждённое.
- Кратко сверь результат по смыслу с шаблоном и прежним пространством, если оно
  было: какие правила потеряны или изменены, появились ли новые ограничения,
  сохранены ли общее назначение областей, важные ограничения материалов
  и возможность продолжить задачи. Исправь непредусмотренные потери и изменения.
- Есть результат первой задачи или явно записанный блокер с продолжением.

В конце кратко сообщи владельцу абсолютный путь OS, что настроено, результат
первой задачи и что осталось проверить. Если создан артефакт, дай ссылку на него.
Для следующего чата дай короткий вход:
«Открой [фактический путь], прочитай INDEX.md, AGENTS.md и system/agent/BOOTSTRAP.md,
продолжи по сохранённому состоянию» — подставь реальный путь.

Чтение файлов в текущем чате не доказывает автоматическое подключение нового.
Если новый чат ещё не проверен, так и укажи; не запускай его без полномочий.

# Миграция существующего пространства

Читай при переходе на стартер папки с материалами или правилами, даже если она
раньше не называлась OS. Для обычной работы миграция не нужна.
Цель: сохранить знания и рабочие правила владельца при адаптации структуры.

## 1. Разобраться и согласовать

До согласования плана сохраняй исходное состояние материалов и инструкций;
создание разделов тоже входит в план. Сам файл плана можно подготовить
в рабочей временной области вне изменяемых материалов.

- Определи старый и целевой корни, фактическую ОС и оболочку. Прочитай старые
  карты и `AGENTS.md`; найди профиль пользователя, память агента, проекты,
  инструменты и действующие точки входа клиентов. Не сканируй соседние папки.
- Сопоставь их с `workspace/`: знания пользователя → `personal/`, карты проектов
  → `projects/`, служебные области → `system/`. Имена папок не доказывают их
  назначение. Код, внешние хранилища и пакеты клиента остаются у своих владельцев.
- Составь один файл плана: исходные и целевые пути, создаваемые разделы,
  переносимые документы шаблона, изменения файлов и правил, ограничения материалов,
  зависимые ссылки и настройки, резервная копия, откат и проверки.
  Используй [основу адаптации из онбординга](README.md#3-подготовь-личную-папку).
  Отметь конфликты, непонятные материалы и уже сломанные ссылки; объясни
  существенные объединения или исключения документов шаблона.
- В чате обычно достаточно трёх коротких пунктов: какая структура появится,
  что переместится и как сохранятся материалы и правила. Назови место копии
  и существенные конфликты. Техническую среду, перечни файлов, откат и проверки
  оставь в файле плана. Дай ссылку на него и получи согласие; читать подробности
  для решения необязательно.

Выполняй фазу 2 после одобрения этого плана. Общее поручение «перейти на стартер»
не означает согласия на ещё неизвестные перемещения и изменения правил.
После согласования сохрани план по месту задачи; отдельная обязательная папка
или реестр для него не нужны. Уже одобренный план повторно
не согласовывай; при продолжении прочитай его и проверь текущее состояние.

## 2. Перенести и проверить

1. Убедись, что в затронутые файлы никто не пишет; иначе согласуй паузу.
   До первого изменения материалов, правил или структуры сохрани и проверь
   копию всех затрагиваемых исходных файлов в согласованном месте
   вне переносимого дерева. Не подменяй его временной папкой; если оно недоступно,
   остановись. Не копируй внешние каталоги по символическим ссылкам и внешний store секретов.
2. Переноси только согласованные материалы. При совпадении путей объединяй
   правила и карты по смыслу; заполненные файлы не заменяй заглушками шаблона.
   Сохрани профиль пользователя, личность агента, память, локальные `AGENTS.md`
   и исходные даты документов.
   Неизвестное оставь на месте и явно отметь, не удаляй как «лишнее».
3. Обнови рабочие карты, относительные и абсолютные ссылки, локальную среду
   в корневом `AGENTS.md` и согласованные клиентские входы. Исторические записи
   не переписывай массовой заменой. Правила и несекретные указатели на внешнее
   хранилище переноси как документы. Значения ключей не читай в контекст и
   не копируй в OS, шаблон или Git; `system/secrets/` хранит только правила и указатели.
4. Сверь материалы с исходниками: содержимое и вложения сохранены, изменения
   ограничены планом. Пройди вход `INDEX.md` → `AGENTS.md` →
   `system/agent/BOOTSTRAP.md` и маршруты к перенесённым задачам. Проверь ссылки
   и внешние пути; отличай старые проблемы от появившихся после переноса.
   Выполни содержательную сверку из [приёмки онбординга](README.md#проверка-результата).
5. Исправь обнаруженные ошибки и повтори затронутые проверки. Если перенос
   небезопасно продолжать, остановись и используй согласованный откат.
   Сообщи новый вход, проверки и нерешённое; проверь и укажи точный путь к резервной копии.

Резервную копию и старый корень автоматически не удаляй. Чтение входных файлов
не доказывает работу нового чата, клиента или сервиса; непроверенное назови явно.
Продолжи с оставшихся действий [шага 4 онбординга](README.md#4-настрой-вход-и-познакомься),
используя уже известные ответы, затем выполни первую задачу и сохрани продолжение.
