# Рабочие правила

## Документы

Для нового поддерживаемого Markdown используй YAML `type` (1–40 символов),
`description` (1–240 символов: содержание и условие чтения), `created` как
дату создания `YYYY-MM-DD` в часовом поясе владельца. Сохраняй исходную дату
при правках/переносе. Если у старого документа дата неизвестна, не выдумывай.
Чужие исходники, внешние навыки и сырые импорты не переписывай под этот формат.

`INDEX.md` — карта области: короткие ссылки с пояснением, когда по ним идти.
Корневой индекс ведёт в разделы, индексы разделов — к нужным материалам.
Ссылки — относительные. Для долговечного результата добавь маршрут в ближайшую
карту. Отдельная карта полезна, когда объединяет материалы или точку продолжения;
не создавай её только ради формы и не запрещай для небольшой задачи.
Карта показывает входы по задачам, не полный список файлов: состав каталога
можно посмотреть средствами текущей среды. Для карты проекта используй
[короткую форму и её ограничения](templates/project.md).
`AGENTS.md` нужен лишь для отличающихся обязательных правил. У процедуры один источник.

## Источники и память

Обсуждение и быстрые черновики не требуют отчёта о проверках или метаданных.
Что сохранять в файлы, определяет [правило передачи](../agent/protocols/handoff.md).
Пометь черновик, если его можно спутать с согласованным решением.
В состоянии задачи предположение не становится фактом только потому,
что сохранено в файле.
Для факта, от которого зависит следующий шаг, достаточно короткого основания:
«со слов владельца», ссылки на документ или команды с результатом и датой.
Например: «Git вернул отказ доступа; причина не установлена», а не «Git сломан».
Перепроверяй при продолжении важное, сомнительное или изменчивое; всю историю
перепроверять не нужно. Не добавляй несущественные технические подробности.

Память ссылается на состояние задачи, не копирует чаты. Предпочтения принадлежат
профилю, состояние — задаче, общие правила — этому разделу. Периодический уход
и автоматизации вводятся только по отдельному решению.

## Реализация и проверки

Простое решение под текущую задачу предпочтительнее заготовок для будущего.
Проверяй наблюдаемый результат; записывай ограничения. Объём тестов согласуй
с проектным контрактом; не создавай постоянный тестовый набор без потребности.
Тяжёлые данные, модели, datasets и кэши держи вне OS и Git-репозиториев кода.
Не скачивай их без согласованной задачи, места и бюджета.

## Публикация

Публикация личной информации требует отдельного решения владельца.
Материал, существенно написанный агентом для публичного размещения,
должен иметь видимое указание на участие ИИ и подтверждённое происхождение.
Не имитируй личное авторство и пережитый опыт человека.
